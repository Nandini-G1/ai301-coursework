# Rubric: is this pull request ready to submit?

Seven required checks and two preferred ones. Each required check maps to one of the four failure families (silent drift, not tested, unreviewable, standards wall); a package that passes all of them is a clear accept. "The plan" always means the accepted plan plus its deviation notes. "Disclosed" means the plan's deviation or deferral notes, or the PR description, state the shortfall or departure in plain words.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The diff's changed files and hunks read against the plan's scope pair (what is in scope, what is not), its named files, and its deviation notes; then each plan step read against the diff. | Every changed file and every hunk does something the plan names, or something a disclosed deviation names; nothing the plan marks "not in scope" appears; and every step the plan promises is present in the diff or is disclosed as deferred or dropped. Tests and the changelog or release-note entry the plan or repo asks for count as in scope. Fail on any undisclosed extra (a new option, flag, setting, rename pass, or rewrite of a function the plan does not name) or any undisclosed missing step. | required |
| description-matches-diff | Each factual claim in the PR description (what changed, what was added, "exactly as planned", "no other changes", "docs updated") read against the diff. | Every claim the description makes about the change is true in the diff, and the description does not call the change faithful to the plan while the diff departs from it. Fail if the description claims something the diff does not contain (more than the diff) or says "nothing else changed" while the diff changes more. Omitting a minor detail is not a false claim. | required |
| repro-before-after | The test-evidence section (and the description, if it carries output) read against the plan's test plan and the issue's reproduction. | The evidence re-runs the plan's failing scenario itself, not a control, a neighboring path, or the unchanged case, and shows actual output (command and result) for the after state on the branch, with the before state shown or quoted alongside it. If the test plan names more than one failure scenario, each is re-run. Fail on assertions without output ("works now", "verified on my machine", "tested locally"), and on evidence that only exercises a path the fix did not change. | required |
| repo-checks-run | The test evidence and the Testing section read against the suite or checks the repo states (PR template, contribution docs, repo facts) and any suite the plan's test plan names. | When the repo or the plan names a test suite or checks, the evidence names each one that was run and shows its outcome (passed, failed with the reason, or "no tests ran"). A failing or empty check reported honestly with its reason passes; "all tests pass" with no command named, or a ticked box with no output behind it, fails. If neither the repo nor the plan names any suite or check, pass on the repro evidence alone. | required |
| diff-clean | Every hunk of the diff, plus the commit list. | The diff contains only the change and the tests and entries that support it. Fail if any hunk adds a debug print or log line, commented-out code, a dead or unused function or variable, a leftover TODO or FIXME, formatting or whitespace churn on lines the fix does not need, an import reshuffle the new code does not require, or an edit unrelated to the issue. One such hunk is enough to fail. Imports the new code actually needs are not churn. | required |
| template-and-asks | The repo's stated asks (repo-facts block in eval mode; the PR template and docs/CONTRIBUTING.md plus scope.md's house rules in live mode) read against the description, the diff, and, in live mode, the branch name. | Every required section of the PR template is present with real content (not left blank or as the template's placeholder text), every required checklist item is addressed truthfully, an issue link is present in the form the template asks for ("Closes #N", "fixes #N"), and any file the repo says a change must carry (changelog, whatsnew, i18n, regenerated docs) is in the diff. Asks the repo states as hints or matters of taste (title polish, screenshots "if appropriate") pass unless visibly ignored. When the repo states no template and no required asks, pass. Live mode adds: the branch name matches `<type>/<issue-number>-<short-description>` with a type of fix, feat, docs, test, refactor, perf, or chore; no Testing box is ticked without matching output in the evidence; the CI box left unticked before opening is correct, not a fail; a seeded-bug fix removes its `@pytest.mark.xfail` markers and any pyproject suppression naming the issue. | required |
| ai-disclosure | The repo's stated AI-use policy (repo facts in eval mode) read against the PR description; in live mode, the Notes for Reviewers section. | When the repo's policy requires disclosing AI use, the description discloses it: which tool or that AI was used, and to what extent, in the author's own words. In eval mode, every package is AI-assisted work, so a required disclosure that is missing fails. When the repo states no AI policy, or a policy that does not require disclosure, pass. In live mode the course always requires it: Notes for Reviewers must say in the author's own words how AI was used on the change. | required |
| commit-messages | The commit list. | Each commit message names what that commit changes (in live mode, in Path Review's Conventional Commits form, `<type>(<scope>): <description>`); messages like "wip", "fix", "misc" fail. | preferred |
| thread-engaged | The issue's thread highlights read against the description. | If a maintainer asked a question or gave a direction the plan adopted, the description engages it by name or substance. If the thread has no such direction, pass. | preferred |

## Verdict rule

Accept only if every required check grades `pass`. Any required check graded `fail` makes the verdict reject. A required check graded `unclear` counts as `fail`, because a claim the package does not let you verify is not ready to submit; grade `unclear` only when the evidence the check needs is genuinely absent from the package, and say what is absent. Preferred checks are graded and reported but never change the verdict, whatever their grade. A shortfall or departure that is disclosed in the plan's deviation notes or the description never fails plan-fidelity or description-matches-diff on its own; the verdict follows the remaining checks.
